## 2. ComfyUI Desktop and memory management
Two desktop apps: legacy `Comfy-Org/desktop` **archived 2026-06-26**, last v0.9.4 (2026-05-28) with ComfyUI v0.22.3, torch 2.10.0+cu130, Python 3.12 (PRIMARY). New **Comfy-Desktop v1.1.6 (2026-10-03)**: relocatable Python 3.13.12 + uv; Comfy-Desktop repo file torch-index-stacks.md documents cu126 and cu128 at torch 2.11.0 (cu128: CC 7.5–12.0). Default stack for a 5070: **NÃO VERIFICADO** (PRIMARY). ComfyUI core **v0.39.0 (2026-10-05)**; portable "python 3.13 and pytorch cuda 13.0".

Flags (cli_args.py, PRIMARY): `--lowvram` ("Doesn't do anything if dynamic vram is enabled"); `--novram`; `--highvram`; `--reserve-vram N` (Windows default `EXTRA_RESERVED_VRAM = 600 MB` "because of the shared vram issue" → **~11.3 GB usable on a 5070**); `--vram-headroom N`; `--cache-none`; `--cache-ram` (default; headroom 10 % RAM, min 2 GB, max 10 GB); `--cache-lru N`; `--disable-smart-memory`; `--async-offload [N]` (default 2, on); `--disable-dynamic-vram` (will be removed), `--enable-dynamic-vram`; `--fast-disk` ("Force disk-backed dynamic loading and offload over unpinned RAM"); `--disable-fast-disk`; `--high-ram`; `--disable-pinned-memory`; `--disable-mmap`; `--mmap-torch-files`; `--fast [fp16_accumulation|fp8_matrix_mult|cublas_ops|autotune]`.

Dynamic VRAM (comfy-aimdo 0.5.5): enabled by default on NVIDIA with torch ≥ 2.8 (main.py, PRIMARY); default since 2026-03 (blog excerpt). comfy-aimdo README: "pytorch VRAM allocator that implements on-demand offloading of model weights"; VBAR virtual-address reservation; torch ≥ 2.8, CUDA ≥ 12.8, "Windows 11 or later, and Linux"; "behaves a lot better on Windows systems with System Memory fallback" (PRIMARY). **Loading = mmap, not RAM copy**: `load_safetensors()` → `ModelMMAP` + `torch.frombuffer`; tensors carry `_comfy_tensor_file_slice`; "working with read-only RAM by design"; `read_tensor_file_slice_into()` reads file→device directly or via 64 MiB pinned window (PRIMARY). `ModelPatcherDynamic.load` logs "...prepared for dynamic VRAM loading … MB Staged". **TE device = GPU when aimdo on** (v0.37.0). **Pinned RAM cap on Windows:** `MAX_PINNED_MEMORY = ram * 0.40` → **~6.4 GB on 16 GB**; eviction when swap > 5 % or available < 512 MB (PRIMARY). **Fast-disk auto-policy (v0.37.0, 2026-09-21)**: issue #16415: "every weight that does not fit in VRAM is re-read from the safetensors file on every sampling step"; 5090/192 GB/38 GB model: 50–90 s/it vs 36 s/it, SSD 100 %; issue #16729 (Windows, 11.9 GB VRAM, 32 GB RAM): "~39 GB of weights are staged against only 11.9 GB of VRAM", ~214.8 GB host→device per run (PRIMARY/REPRODUCED). Legacy partial loading (dynamic off): `lowvram_model_memory = free − minimum_memory_required`; `MIN_WEIGHT_MEMORY_RATIO = 0.0` on NVIDIA; logs "loaded partially; … MB loaded, … MB offloaded" (PRIMARY).

Known Dynamic-VRAM problems (REPRODUCED): #14618 (3060 12 GB, 32 GB RAM; re-read from disk every prompt change; 49–103 s vs 0.03 s); #14276 (5070 Ti Win11; after dtype switch every prompt reloads; 23–28 s → 120–190 s; not with `--disable-dynamic-vram`); #16551 (5070 Ti; dynamic VRAM prevents `fp8_e4m3fn_fast`: flux1-dev 1.07 it/s vs 1.72 it/s); #15255 (Desktop/Windows torch 2.10+cu130; host-buffer read → CUDA OOM; workarounds `--cuda-device 0`, `--disable-pinned-memory`, `--disable-dynamic-vram`); #14940 (8 GB/32 GB; pinned memory pushed RAM to ceiling → `--disable-pinned-memory`); **#12334 (2026-02-06, legacy path): RTX 3060 12 GB + 16 GB RAM, Windows, FLUX.1-dev FP8: "10–20 minutes before the KSampler actually starts", heavy swapping**; #12541 (5060 Ti 16 GB, 32 GB RAM; Qwen Image Edit 4 refs @2K: RAM to 32 GB, constant paging); #14433: klein 9B Q8 + Qwen3-8B Q8 TE on 13 GB RAM — RAM 90–96 %, OOM loading UNet.

Subprocess / separate venv: no official core API. Comfy-Org **pyisolate** (isolated venvs, JSON-RPC, tensors via /dev/shm, bubblewrap Linux; Windows not mentioned; `pyisolate-support` branch) (PRIMARY). Community **comfy-env** (pixi envs, persistent subprocesses, UDS/TCP on Windows); WorkerKeeper ~2 GB RAM per idle worker (excerpt). Any custom node can spawn `subprocess`; RAM cost is the issue on 16 GB.

## 5. Text encoders
- Qwen2.5-VL-7B: fp8_scaled ≈ 9.38 GB; GGUF Q4_K_M ≈ 4.68 GB + mmproj f16 1.35 GB (REPRODUCED; ComfyUI-GGUF supports qwen2vl + mmproj, PRIMARY).
- T5-XXL: fp8 ≈ 4.9 GB, fp16 ≈ 9.5 GB (INFERRED).
- Mistral-Small-3.2-24B (FLUX.2 dev): fp8 = **18 GB**, bf16 35.6 GB; GGUF Q4_K_M ≈ 14 GB (INFERRED). Cannot be RAM- or VRAM-resident → streamed from disk.
- Strategy: with Dynamic VRAM, TE placed on GPU (v0.37.0) and staged via mmap; `--lowvram` TE-on-CPU only applies with `--disable-dynamic-vram`. #14433: 9B Q8 + 8B TE Q8 OOMs at 13 GB RAM.

## 6. Windows-specific
- Pagefile/commit: allocations fail when commit charge > RAM + pagefile ("The paging file is too small", error 1455) even with free RAM; counters `\Memory\Committed Bytes`, `\Memory\Commit Limit`. Community guidance for 16 GB: pagefile max ≈ 32 GB (30–48 GB peaks observed for FLUX) on SSD. mmap'd read-only safetensors pages are file-backed and should not consume commit; pinned (`cudaHostRegister`) buffers do — INFERRED; ComfyUI caps pinning at 40 % RAM on Windows.
- WSL2: default VM memory = min(50 % RAM, 8 GB) on Windows 11 → 8 GB; Dynamic VRAM "WSL not planned" (excerpt). **Not viable for 20B models on 16 GB.**
- HAGS: Puget (4080): disabling gave "slight improvement" in SD-WebUI/ComfyUI (REPRODUCED).
- CUDA Sysmem Fallback Policy: driver 536.40 spill to shared memory ("lower speeds"); 546.01 setting; "Prefer No Sysmem Fallback … stable at the risk of a crash". ComfyUI reserves +600 MB on Windows; comfy-aimdo "behaves a lot better on Windows with System Memory fallback". Forcing "No Fallback" converts slowdowns into hard OOMs — INFERRED; test both.

## 7. Measurement tooling
- VRAM: `torch.cuda.reset_peak_memory_stats()`; `max_memory_allocated()` (live tensors); `max_memory_reserved()` (pool, closer to nvidia-smi); NVML `nvmlDeviceGetMemoryInfo().used` whole device incl. context — sample in a thread; `nvidia-smi --query-gpu=memory.used --format=csv -l 1`.
- RAM/commit (Windows): `Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit','\Memory\Page Faults/sec','\Memory\Pages Input/sec'` (hard faults ≈ Pages Input/sec); `Get-Process | Select WorkingSet64, PrivateMemorySize64`; `psutil.Process().memory_info()` → wset, private, pagefile, num_page_faults.
- ComfyUI logs: `--verbose DEBUG` prints `Model loaded: … ram_mb=… vram_mb=…`, "Requested to load …", "loaded completely/partially …", "prepared for dynamic VRAM loading … MB Staged", "Using async weight offloading with 2 streams", "DynamicVRAM support detected and enabled", "Prompt executed in X seconds".

## 8. Likely infeasible on 12 GB + 16 GB RAM (evidence-based)
1. **FLUX.2 dev (32B) — infeasible in practice**: Q4 ≈ 19 GB + 18 GB fp8 / ≥14 GB GGUF Mistral TE exceeds VRAM and RAM; streams from NVMe every step; only sub-24 GB report uses a remote TE; 9B+8B GGUF pair already OOMs at 13 GB RAM.
2. **Step1X-Edit — infeasible** (min 18 GB VRAM).
3. **IDM-VTON — infeasible without offload** (≥16 GB).
4. **HiDream-E1 — no 12 GB evidence; infeasible until verified.**
5. **WSL2** (8 GB VM RAM default, no Dynamic VRAM).
6. **Qwen-Image-Edit-2509/2511 (20B) — feasible but marginal:** Q4 GGUF (11.9–13.1 GB) or Nunchaku NVFP4 (~12.7 GB) exceeds ~11.3 GB usable; part of DiT + 9.4 GB fp8 (or 4.7 GB Q4) VL encoder must live in RAM/disk; Windows pinning capped ~6.4 GB; only 16 GB-RAM data point for a *12B* fp8 model showed 10–20 min stalls (#12334); 32 GB machine saturated on 2K multi-ref (#12541). Expect minutes per image; 60-min budget plausible with Lightning 4/8-step LoRAs, but **no measured 12 GB + 16 GB number exists** — NÃO VERIFICADO.
7. **Comfortably feasible:** FLUX.1 Kontext dev via Nunchaku INT4/FP4 (~6.8 GB) or fp8 (~12 GB partial offload); FLUX.2 klein 4B (8.4 GB fp8); CatVTON (<8 GB); OmniGen2 with CPU offload (~8.5 GB, RAM tight); BAGEL NF4 borderline.
